    핵심 개념 한국어 요약

    스레드(thread)는 운영체제 스레드이고, thread::spawn이 클로저를 새 스레드에서 실행합니다. 새 스레드는 부모 함수보다 오래 살 수 있으므로 지역 변수를 빌려 쓰지 못하고 move로 소유권을 가져가야 합니다. 결과는 join()으로 받습니다. 스레드가 패닉하면 join()이 Err를 돌려줍니다.

    스레드 사이에 값을 보내는 방법이 채널(channel)입니다. mpsc는 "여러 생산자, 하나의 소비자(multi-producer, single-consumer)"의 약자로, 송신 쪽 tx를 clone해 여러 스레드에 나눠 주고 수신 쪽 rx가 받습니다. 값은 보낸 순간 소유권이 넘어갑니다. 값을 공유해야 한다면 Arc<Mutex<T>>를 씁니다. Arc는 원자적 참조 카운트로 여러 스레드가 같은 값을 소유하게 해 주고, Mutex는 한 번에 한 스레드만 값을 고치게 합니다. 중요한 차이는 Java의 synchronized와 달리 Mutex<T>가 데이터를 안에 품고 있다는 점입니다. 락을 잡지 않으면 데이터에 아예 접근할 수 없습니다.

    Send와 Sync는 컴파일러가 알아서 붙이는 표시 trait입니다. Send는 "값을 다른 스레드로 옮겨도 안전하다", Sync는 "여러 스레드가 &T로 동시에 가리켜도 안전하다"는 뜻입니다. thread::spawn은 클로저가 Send일 것을 요구하고, 컴파일러가 클로저에 들어 있는 값들을 하나씩 따져 봅니다. 참조 카운트를 원자적으로 세지 않는 Rc는 Send가 아니라서 막히고, Arc는 통과합니다. 이것이 Rust가 "데이터 경쟁(data race)은 컴파일 오류"라고 말하는 근거입니다.

    async/await는 스레드 없이도 "기다리는 동안 다른 일을 하게" 해 주는 문법입니다. async fn은 호출해도 실행되지 않고 퓨처(future)라는 값을 돌려줄 뿐이며, .await를 하거나 런타임이 실행(poll)해야 진행됩니다. 퓨처를 실제로 돌리는 런타임(runtime)은 표준 라이브러리에 없어서 tokio 같은 크레이트를 씁니다. 여러 작업이 사실상 동시에 진행되는 것은 tokio::join!이나 tokio::spawn을 썼을 때입니다. .await를 순서대로 쓰면 직렬입니다. Send는 tokio::spawn에서 문제가 됩니다. 스레드 풀(멀티스레드 런타임)이 spawn한 작업을 .await에서 멈춘 사이에 다른 스레드로 옮길 수 있으므로, tokio::spawn에 넘기는 퓨처는 Send여야 하고, 그러려면 .await 너머로 들고 있는 값이 모두 Send여야 합니다(tokio 공식 튜토리얼의 "Send bound"). 반면 #[tokio::main]이 만든 main의 퓨처는 spawn되지 않고 현재 스레드에서 실행(block_on)되므로 Send가 필요 없습니다. 락 가드를 쥔 채 .await하는 퓨처를 tokio::spawn에 넘기면 막히는 이유가 여기에 있습니다.

    2. 스레드 만들고 기다리기, move (mine.rs, 1단계 의존)

      mine.rs에 입력합니다. 첫 줄 use는 뒤 단계에서 쓰는 것까지 미리 가져옵니다(지금은 "사용되지 않음" 경고가 나도 정상입니다).

      use std::sync::{Arc, Mutex, mpsc};
use std::thread;

fn spawn_and_join() {
    let handle = thread::spawn(|| (1..=100).sum::<u32>());
    println!("메인 스레드: 작업이 끝나기를 기다립니다");
    let total = handle.join().unwrap();
    println!("1부터 100까지의 합 = {total}");
}

fn move_into_thread() {
    let mut names = vec![String::from("alice"), String::from("bob")];
    names.push(String::from("carol"));
    let handle = thread::spawn(move || names.len());
    println!("스레드가 센 이름 수 = {}", handle.join().unwrap());
}

    4. 채널로 값 주고받기, drop(tx)의 의미 (mine.rs, 2단계 의존)

      세 스레드가 각자 계산한 값을 채널로 보냅니다. mine.rs에 아래 함수를 추가하고 main에 channel_workers();를 덧붙여 실행합니다.

      fn channel_workers() {
    let (tx, rx) = mpsc::channel();
    for worker in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            let result = (worker + 1) * 100;
            tx.send((worker, result)).unwrap();
        });
    }
    drop(tx);

    let mut results: Vec<(i32, i32)> = rx.iter().collect();
    results.sort();
    println!("채널로 받은 결과 = {results:?}");
}

      새로 붙는 한 줄입니다.

      채널로 받은 결과 = [(0, 100), (1, 200), (2, 300)]

      스레드가 끝나는 순서는 실행마다 다를 수 있어서 results.sort()로 정렬해 출력을 고정했습니다. drop(tx)가 핵심입니다. rx.iter()는 모든 송신자가 사라질 때 끝나는데, 반복문 앞에서 clone하고 남은 원본 tx를 버리지 않으면 영원히 기다립니다. 직접 확인합니다. 아래 코드를 scratch.rs에 넣고 cargo run -p lesson10 --example scratch로 실행하세요.

      use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    for worker in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(worker * 100).unwrap();
        });
    }

    for value in rx.iter() {
        println!("받음: {value}");
    }
    println!("모두 받았습니다");
}

      세 값을 받은 뒤 프로그램이 끝나지 않고 멈춰 있습니다(받는 순서는 달라질 수 있습니다). 터미널에서 Ctrl+C로 끝냅니다. 컴파일러 메시지는 없는 런타임 증상이라 실제로 4초 이상 끝나지 않는 것을 확인했습니다.

      받음: 0
받음: 100
받음: 200

      해결은 for 루프 앞에 drop(tx); 한 줄을 넣는 것입니다.

      루프의 첫 바퀴에서 counter가 클로저로 이동하고, 둘째 바퀴에서 이미 이동된 값을 또 쓰려는 것입니다. 소유자가 여럿이어야 하니 Arc가 필요합니다. 완성형을 mine.rs에 입력합니다. 스레드에 이름을 붙이는 thread::Builder는 디버거에서 스레드를 구분하기 위해서입니다.

      fn shared_counter() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = Vec::new();
    for id in 0..4 {
        let counter = Arc::clone(&counter);
        let handle = thread::Builder::new()
            .name(format!("worker-{id}"))
            .spawn(move || {
                for _ in 0..1000 {
                    *counter.lock().unwrap() += 1;
                }
            })
            .unwrap();
        handles.push(handle);
    }
    for handle in handles {
        handle.join().unwrap();
    }
    println!("최종 카운터 = {}", *counter.lock().unwrap());
}

      이어서 스코프 스레드도 입력합니다. thread::scope 안에서 만든 스레드는 스코프가 끝나기 전에 반드시 합류하므로, Arc 없이도 지역 변수를 빌려 쓸 수 있습니다.

      fn scoped_threads() {
    let numbers: Vec<i32> = (1..=6).collect();
    let (left, right) = numbers.split_at(3);
    let (left_sum, right_sum) = thread::scope(|scope| {
        let a = scope.spawn(|| left.iter().sum::<i32>());
        let b = scope.spawn(|| right.iter().sum::<i32>());
        (a.join().unwrap(), b.join().unwrap())
    });
    println!("스코프 스레드 합계 = {left_sum} + {right_sum}");
}

    7. async/await와 tokio (mine_async.rs, 1단계 의존)

      src/bin 폴더에 새 파일 mine_async.rs를 만들고 입력합니다. 한 파일에 전부 들어 있습니다.

      use std::time::{Duration, Instant};

use tokio::time::{sleep, timeout};

async fn fetch_user(id: u32) -> String {
    sleep(Duration::from_millis(100)).await;
    format!("사용자#{id}")
}

fn rounded_ms(started: Instant) -> u128 {
    started.elapsed().as_millis() / 100 * 100
}

#[tokio::main]
async fn main() {
    let started = Instant::now();
    let first = fetch_user(1).await;
    let second = fetch_user(2).await;
    println!(
        "순차 실행: {first}, {second} (약 {}ms)",
        rounded_ms(started)
    );

    let started = Instant::now();
    let (third, fourth) = tokio::join!(fetch_user(3), fetch_user(4));
    println!(
        "join! 실행: {third}, {fourth} (약 {}ms)",
        rounded_ms(started)
    );

    let handles: Vec<_> = (5..=7).map(|id| tokio::spawn(fetch_user(id))).collect();
    for handle in handles {
        println!("spawn 결과: {}", handle.await.unwrap());
    }

    match timeout(Duration::from_millis(30), fetch_user(8)).await {
        Ok(user) => println!("제때 도착: {user}"),
        Err(error) => println!("시간 초과: {error}"),
    }
}

      읽는 법입니다.

      • #[tokio::main]은 main을 async로 만들고 tokio 런타임을 자동으로 띄웁니다. features에 macros와 rt-multi-thread가 필요한 이유입니다.
      • 순차 실행은 .await를 두 번 이어 써서 100ms + 100ms, 약 200ms가 걸립니다. join!은 두 퓨처를 함께 진행시켜 약 100ms에 끝납니다. 출력은 100ms 단위로 내림한 값이라 PC 성능에 따라 200ms와 100ms가 이 값과 다르게 나올 수 있습니다(매우 느린 PC 한정).
      • tokio::spawn은 퓨처를 독립 작업(task)으로 띄우고 JoinHandle을 돌려줍니다. 핸들을 순서대로 .await하므로 결과 순서는 5, 6, 7로 고정됩니다.
      • timeout은 지정한 시간 안에 끝나지 않으면 Err를 돌려줍니다. 30ms 안에 100ms짜리 작업은 끝나지 못해 deadline has elapsed가 나옵니다.

    익숙함이 만드는 함정 ① — Mutex는 데이터를 감쌉니다Java·Kotlin의 synchronized 블록은 락과 데이터가 별개라 락을 잊어도 컴파일이 됩니다. Rust의 Mutex<T>는 lock()으로 가드를 얻어야만 T에 접근할 수 있어서 잊을 수가 없습니다. 대신 락을 잡은 스레드가 패닉하면 락이 "오염(poison)"되어 다음 lock().unwrap()이 실패합니다(아래 참고).
    익숙함이 만드는 함정 ② — async fn 호출은 실행이 아닙니다Kotlin의 launch { }나 Python의 asyncio.create_task는 부르는 순간 일정이 잡히지만, Rust는 퓨처를 .await하거나 spawn해야 움직입니다. .await를 빼먹으면 컴파일은 되고 아무 일도 일어나지 않습니다. 컴파일러가 내는 경고를 놓치지 마세요.
    익숙함이 만드는 함정 ③ — async 안에서 오래 막으면 런타임이 막힙니다async 작업 안에서 std::thread::sleep이나 무거운 계산을 하면 그 작업이 올라 있는 런타임 스레드가 통째로 묶입니다. 기다림은 tokio::time::sleep(...).await처럼 비동기 버전을 쓰고, 무거운 계산이나 블로킹 호출은 tokio::task::spawn_blocking으로 따로 돌리는 것이 권장 방식입니다(tokio 튜토리얼 참고). 이 레슨의 실험으로 직접 확인한 내용은 아닙니다.

    문제 1. 스레드로 나눠 더하기

    pub fn parallel_sum(numbers: &[u64], workers: usize) -> u64를 만드세요. 숫자들을 workers개 구간으로 나눠 각 구간의 합을 스레드가 계산하고, 마지막에 모두 더합니다. workers가 0이면 패닉합니다. Arc 없이 빌려 쓰는 thread::scope를 써 보세요.

    완료 조건: 1..=1000의 합이 workers가 4일 때도 7일 때도 500500, 빈 슬라이스는 0이다. cargo test -p lesson10의 parallel_sum_* 두 테스트가 통과한다.

    힌트 보기

    구간 크기는 numbers.len().div_ceil(workers)이고(최소 1), numbers.chunks(구간 크기)가 구간을 나눠 줍니다. 각 구간에서 scope.spawn(move || chunk.iter().sum::<u64>())를 만들어 핸들을 모아 두고, 마지막에 join().unwrap()한 값을 합칩니다. move를 붙여도 chunk는 참조라 복사되는 것이 아니라 빌림이 옮겨질 뿐입니다.

    정답 예시 보기 
    pub fn parallel_sum(numbers: &[u64], workers: usize) -> u64 {
    assert!(workers > 0, "workers는 1 이상이어야 합니다");
    let chunk_size = numbers.len().div_ceil(workers).max(1);
    thread::scope(|scope| {
        let handles: Vec<_> = numbers
            .chunks(chunk_size)
            .map(|chunk| scope.spawn(move || chunk.iter().sum::<u64>()))
            .collect();
        handles
            .into_iter()
            .map(|handle| handle.join().unwrap())
            .sum()
    })
}

    문제 2. 순서를 지키는 병렬 조회

    pub async fn fetch_all(ids: Vec<u32>) -> Vec<String>을 만드세요. 각 id마다 tokio::spawn으로 fetch_user를 띄워 동시에 진행시키되, 결과는 입력 순서대로 돌려줍니다.

    완료 조건: fetch_all(vec![3, 1, 2])가 ["사용자#3", "사용자#1", "사용자#2"]를 돌려준다. cargo test -p lesson10의 fetch_all_keeps_input_order가 통과한다.

    힌트 보기

    먼저 모든 spawn을 끝내 핸들을 Vec에 모읍니다. 그다음 핸들을 순서대로 .await하면 결과 순서가 입력 순서와 같아집니다. 반복문 안에서 spawn과 .await를 한꺼번에 하면 직렬이 됩니다.

    정답 예시 보기 
    pub async fn fetch_user(id: u32) -> String {
    sleep(Duration::from_millis(50)).await;
    format!("사용자#{id}")
}
    pub async fn fetch_all(ids: Vec<u32>) -> Vec<String> {
    let handles: Vec<_> = ids
        .into_iter()
        .map(|id| tokio::spawn(fetch_user(id)))
        .collect();
    let mut users = Vec::new();
    for handle in handles {
        users.push(handle.await.unwrap());
    }
    users
}
    #[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn parallel_sum_matches_sequential_sum() {
        let numbers: Vec<u64> = (1..=1000).collect();
        assert_eq!(parallel_sum(&numbers, 4), 500_500);
        assert_eq!(parallel_sum(&numbers, 7), 500_500);
        assert_eq!(parallel_sum(&[], 3), 0);
    }

    #[test]
    #[should_panic(expected = "workers")]
    fn parallel_sum_rejects_zero_workers() {
        parallel_sum(&[1, 2, 3], 0);
    }

    #[tokio::test]
    async fn fetch_all_keeps_input_order() {
        let users = fetch_all(vec![3, 1, 2]).await;
        assert_eq!(users, vec!["사용자#3", "사용자#1", "사용자#2"]);
    }

    let worker = Arc::clone(&data);
    let result = thread::spawn(move || {
        let _guard = worker.lock().unwrap();
        panic!("락을 잡은 채로 패닉");
    })
    .join();
    println!("스레드 결과는 Err인가? {}", result.is_err());
    println!("{}", data.lock().unwrap());
}
