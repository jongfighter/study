    핵심 개념 한국어 요약

    Rust의 코드 단위는 네 겹입니다. 크레이트(crate)는 컴파일 한 번의 단위로 실행 파일(binary) 또는 라이브러리(library)입니다. 패키지(package)는 Cargo.toml 하나로 정의되는 빌드 단위이며 라이브러리 크레이트 최대 1개와 실행 파일 크레이트 여러 개를 담습니다. 모듈(module)은 크레이트 안의 이름 공간이자 접근 제한의 경계입니다. 워크스페이스(workspace)는 패키지 여러 개를 묶어 Cargo.lock과 target 폴더를 공유하게 합니다. Gradle로 옮기면 패키지가 서브프로젝트, 워크스페이스가 멀티 모듈 루트 프로젝트에 해당합니다.

    가시성(visibility)의 기본값은 비공개입니다. Kotlin에서 아무것도 안 쓰면 public인 것과 반대입니다. 접근 제한의 단위는 클래스가 아니라 모듈이며, 같은 모듈 안에서는 서로의 비공개 항목(구조체 필드 포함)을 볼 수 있습니다. 밖에 보이려면 pub을, 같은 크레이트 안에서만 보이게 하려면 pub(crate)(Kotlin의 internal과 비슷)를 씁니다.

    파일과 모듈은 명시적으로 연결해야 합니다. src/task.rs를 만든다고 자동으로 컴파일되지 않고, 크레이트 루트(lib.rs 또는 main.rs)에 mod task;라고 선언해야 그 파일이 모듈 트리에 들어옵니다. 모듈 안의 항목은 crate::task::Task(루트부터), super::(부모 모듈), self::(현재 모듈) 경로로 가리키고, use는 긴 경로에 짧은 이름을 붙입니다. pub use는 안쪽 항목을 바깥 이름으로 다시 내보내 사용자에게 보이는 API 모양을 정리합니다.

    테스트는 세 종류입니다. 단위 테스트는 같은 파일 아래 #[cfg(test)] mod tests에 쓰며 use super::*;로 위쪽 코드를 가져옵니다. cfg(test) 덕분에 이 코드는 테스트 빌드에서만 컴파일됩니다. 통합 테스트는 tests/ 폴더에 두며 각 파일이 별도 크레이트로 컴파일되어 오직 공개 API만 쓸 수 있습니다. 문서 테스트(doc test)는 /// 주석 안 코드 블록이 자동으로 컴파일·실행되어, 예제가 낡지 않게 지켜 줍니다. 세 가지 모두 cargo test 한 번으로 돕니다.

    3. 비공개 필드와 생성자로 규칙 지키기 (2단계 의존)

      src/task.rs를 열고 Task 구조체를 봅니다. 필드에 pub이 없으므로 이 모듈 밖에서는 직접 읽거나 만들 수 없습니다.

      #[derive(Debug, Clone, PartialEq)]
pub struct Task {
    id: u32,
    title: String,
    done: bool,
}

      대신 공개 함수 new가 유일한 생성 경로이고, 여기서 제목 규칙을 검사합니다. pub(crate) fn reopen은 같은 크레이트 안에서만 보이고, validate_title은 pub이 없어 이 파일 안에서만 쓰입니다.

      impl Task {
    pub fn new(id: u32, title: &str) -> Result<Task, TaskError> {
        let title = validate_title(title)?;
        Ok(Task {
            id,
            title,
            done: false,
        })
    }

    pub fn id(&self) -> u32 {
        self.id
    }

    pub fn title(&self) -> &str {
        &self.title
    }

    pub fn is_done(&self) -> bool {
        self.done
    }

    pub fn complete(&mut self) {
        self.done = true;
    }

    pub fn toggle(&mut self) {
        if self.done {
            self.reopen();
        } else {
            self.complete();
        }
    }

    pub fn rename(&mut self, title: &str) -> Result<(), TaskError> {
        self.title = validate_title(title)?;
        Ok(())
    }

    pub(crate) fn reopen(&mut self) {
        self.done = false;
    }
}
      fn validate_title(title: &str) -> Result<String, TaskError> {
    let title = normalize_title(title);
    if title.is_empty() {
        return Err(TaskError::EmptyTitle);
    }
    let actual = title.chars().count();
    if actual > MAX_TITLE_CHARS {
        return Err(TaskError::TitleTooLong {
            max: MAX_TITLE_CHARS,
            actual,
        });
    }
    Ok(title)
}

      이 설계의 요점은 "잘못된 Task는 만들 수 없다"를 타입이 보장한다는 것입니다. Kotlin에서 data class에 init { require(...) }를 두는 것과 같은 목적이지만, Rust는 필드 자체를 숨겨서 우회로를 막습니다. 에디터에서 validate_title을 Ctrl+Shift+O로 찾아 점프해 보세요.

mod tests {
    use super::*;

    #[test]
    fn new_normalizes_title() {
        let task = Task::new(1, "  보고서   작성 ").unwrap();
        assert_eq!(task.title(), "보고서 작성");
        assert!(!task.is_done());
    }

    #[test]
    fn empty_title_is_rejected() {
        assert_eq!(Task::new(1, "   "), Err(TaskError::EmptyTitle));
    }

    #[test]
    fn too_long_title_reports_lengths() {
        let long = "가".repeat(MAX_TITLE_CHARS + 1);
        assert_eq!(
            Task::new(1, &long),
            Err(TaskError::TitleTooLong {
                max: MAX_TITLE_CHARS,
                actual: MAX_TITLE_CHARS + 1,
            })
        );
    }

    #[test]
    fn toggle_flips_done_back_and_forth() -> Result<(), TaskError> {
        let mut task = Task::new(7, "운동")?;
        task.toggle();
        assert!(task.is_done());
        task.toggle();
        assert!(!task.is_done());
        Ok(())
    }

    #[test]
    #[ignore = "예시: 평소에는 건너뛰고 필요할 때 --ignored로 실행합니다"]
    fn slow_example() {
        let titles: Vec<String> = (0..10_000).map(|n| format!("할 일 {n}")).collect();
        assert_eq!(titles.len(), 10_000);
    }
}

      /// 제목을 URL에 쓸 수 있는 소문자 slug로 바꿉니다.
///
/// 영문 소문자·숫자만 남기고 나머지 글자는 `-` 하나로 합칩니다.
/// 한글은 이 예제의 규칙에서 빠지므로 한글만 있는 제목은 빈 문자열이 됩니다.
///
/// ```
/// use lesson09::text::slugify;
///
/// assert_eq!(slugify("Write the  Report!"), "write-the-report");
/// assert_eq!(slugify("보고서"), "");
/// ```
pub fn slugify(title: &str) -> String {
    let mut slug = String::new();
    for ch in title.chars() {
        if is_slug_char(ch) {
            slug.push(ch.to_ascii_lowercase());
        } else if !slug.is_empty() && !slug.ends_with('-') {
            slug.push('-');
        }
    }
    slug.trim_end_matches('-').to_string()
}

    익숙함이 만드는 함정 ① — 기본이 비공개입니다Kotlin 습관대로 필드와 함수를 만들면 다른 파일에서 쓰려는 순간 is private 오류가 납니다. 반대로 getter를 일일이 만드는 대신 pub fn title(&self) -> &str 같은 읽기 전용 메서드로 필요한 만큼만 열어 주는 것이 Rust다운 설계입니다.
    익숙함이 만드는 함정 ② — 파일을 만들었다고 컴파일되지 않습니다JVM 프로젝트는 소스 폴더의 파일이 모두 대상이지만, Rust는 mod 이름;으로 선언한 파일만 크레이트에 들어옵니다. 새 파일을 만들고 오류가 나면 먼저 mod 선언을 확인하세요.
    익숙함이 만드는 함정 ③ — 테스트가 제품 코드와 같은 파일에 있습니다Gradle은 src/test를 따로 두지만 Rust 단위 테스트는 같은 파일 끝에 있습니다. 걱정할 필요는 없습니다. #[cfg(test)]가 붙은 코드는 테스트 빌드에서만 컴파일되고 실행 파일에는 들어가지 않습니다. 비공개 함수까지 테스트할 수 있다는 장점도 있습니다.

    1. 테스트 보기 설정은 7단계에서 임시 프로필로 이미 체험했습니다
