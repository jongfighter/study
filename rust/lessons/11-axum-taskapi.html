    axum으로 만드는 Task API

    지금까지 배운 구조체·trait·모듈·async를 한데 모아 Task REST API를 만듭니다. PATCH는 보낸 필드만 고치고, 제목을 검증하고, 상태 코드와 에러 본문을 일정하게 돌려주는 규약을 지키면서 axum의 라우팅과 추출기(Path·State·Json), serde, 에러 응답(IntoResponse)을 씁니다. .http 파일·curl·oneshot 통합 테스트·디버거로 실제 동작을 확인합니다.

    • 소요 약 150분
    • 난이도 ★★★★☆
    • 선행 레슨 10
    • 실습 폴더 lab/lesson11

    GOAL학습 목표

    • Router에 /tasks/{id} 같은 경로와 핸들러를 연결하고 Path·State·Json 추출기로 요청을 받을 수 있다.
    • serde의 Serialize/Deserialize로 JSON 요청·응답 구조체를 만들고, PATCH 부분 수정용으로 Option 필드를 쓸 수 있다.
    • IntoResponse를 구현한 에러 enum으로 상태 코드와 {"error":"..."} 본문을 일관되게 돌려주고, 검증 순서와 상태 코드(201·204·404·400) 규약을 지킬 수 있다.
    • tower::ServiceExt::oneshot으로 서버를 띄우지 않고 통합 테스트를 작성할 수 있다.
    • VS Code의 tasks.json(Ctrl+Shift+B), launch.json(F5), .http 파일(Ctrl+Alt+R)로 빌드·실행·요청·디버깅 흐름을 한 번에 돌릴 수 있다.

    핵심 개념 한국어 요약

    axum은 tokio와 hyper 위에 만든 웹 프레임워크로, 매크로 없이 함수와 타입으로 라우팅을 짭니다. 핸들러(handler)는 async fn이고, 인자 하나하나가 추출기(extractor)입니다. 인자 타입이 곧 "요청의 어느 부분을 어떻게 파싱할지"를 정합니다. Path<String>은 경로의 {id}를 문자열로, Json<T>는 본문을 T로, State<S>는 앱 전체가 공유하는 값을 꺼냅니다(?limit=10 같은 쿼리 파라미터를 꺼내는 Query<T>는 레슨 12에서 씁니다). 요청 본문을 읽어 가는 추출기(Json)는 반드시 마지막 인자여야 합니다.

    핸들러의 반환 타입은 IntoResponse를 구현한 무엇이든 됩니다. Json<T>, (StatusCode, Json<T>), StatusCode가 그렇고, Result<T, E>도 T와 E 둘 다 IntoResponse이면 됩니다. 그래서 에러 enum에 IntoResponse를 구현해 두면 핸들러 안에서 ?로 에러를 던질 수 있고 상태 코드와 본문이 한곳에서 결정됩니다. Spring의 @ExceptionHandler/@ControllerAdvice가 하던 일을 타입 시스템으로 하는 셈입니다.

    공유 상태는 Router::with_state(값)으로 넣고 핸들러에서 State(값)으로 꺼냅니다. 요청마다 값이 복제(Clone)되어 전달되므로, 저장소 안에 Arc<Mutex<...>>(레슨 10)를 두어 복제본이 같은 데이터를 가리키게 합니다. serde는 구조체와 JSON을 오가는 라이브러리이고, #[derive(Serialize, Deserialize)] 한 줄이 Jackson의 매핑 코드를 대신합니다.

    테스트에서는 axum의 Router가 tower::Service라는 점을 이용합니다. oneshot(request)는 서비스를 소비하며 요청 하나를 보내고 응답을 돌려줍니다. 포트를 열지 않고 네트워크 없이 요청 처리 전체(라우팅, 추출, 핸들러, 에러 변환)를 검증하는 것이 FastAPI의 TestClient, Spring의 MockMvc와 같은 역할입니다.

    HANDS-ON따라하기

    이 레슨의 Task API는 다음 규약을 지킵니다. 응답 JSON은 id, title, done, created_at 네 필드이고 id는 1부터 1씩 커지는 정수입니다. 생성은 201, 삭제는 204(본문 없음), 없는 id는 404, 잘못된 입력은 400이며, 에러 본문은 모두 {"error":"..."} 모양입니다. 제목은 앞뒤 공백을 떼고 비어 있거나 100자를 넘으면 400입니다. PATCH는 보낸 필드만 고치고, 고칠 필드가 하나도 없으면 400입니다. Go 코스를 먼저 하셨다면 그 코스의 Task API와 같은 규약이며, 달라지는 점은 아래 "비교" 절의 마지막 하위 절에 모아 두었습니다.

    2. 모델·serde와 메모리 저장소 (model.rs·store.rs, 1단계 의존)

      Task는 응답으로 나가므로 Serialize, 요청 본문인 CreateTask와 UpdateTask는 들어오므로 Deserialize입니다. 두 요청 구조체의 필드가 Option인 이유는 서로 다릅니다. UpdateTask는 PATCH가 "보낸 필드만 고친다"이기 때문입니다(Kotlin의 String?, Boolean?과 같은 역할이고, JSON에 키가 없으면 None이 됩니다). CreateTask의 title은 키가 없거나 null이어도 serde가 거절하지 않게 해서, 핸들러가 제목 검증 에러(400 "title은 비어 있을 수 없습니다")로 답하게 하려는 것입니다. #[serde(deny_unknown_fields)]는 모르는 필드가 오면 거절하는 설정으로, Jackson의 FAIL_ON_UNKNOWN_PROPERTIES를 켠 것과 같습니다(titel 같은 오타가 400이 됩니다).

      use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, PartialEq, Serialize)]
pub struct Task {
    pub id: u64,
    pub title: String,
    pub done: bool,
    pub created_at: String,
}

#[derive(Debug, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct CreateTask {
    pub title: Option<String>,
}

#[derive(Debug, Default, Deserialize)]
#[serde(deny_unknown_fields)]
pub struct UpdateTask {
    pub title: Option<String>,
    pub done: Option<bool>,
}

      이 레슨의 JSON 모양은 {"id": 1, "title": "...", "done": false, "created_at": "2026-11-15T15:51:23.4881677Z"}입니다. id는 1부터 1씩 커지는 정수이고, created_at은 RFC 3339 UTC 문자열입니다. 소수점 아래는 끝의 0을 떼고(0이면 소수점 자체를 빼고) 붙이는 규칙인데, 시간 라이브러리를 더하지 않으려고 clock.rs에서 표준 라이브러리만으로 이 규칙을 직접 구현했습니다. 실서비스에서는 time이나 chrono 크레이트를 쓰는 것이 보통입니다.

      /// 현재 시각을 RFC 3339 UTC 문자열로 돌려줍니다. 소수점 아래는 0이 아닐 때만, 끝의 0을 뺀 채 붙입니다.
pub fn now_rfc3339() -> String {
    let elapsed = SystemTime::now()
        .duration_since(UNIX_EPOCH)
        .unwrap_or_default();
    format_timestamp(elapsed.as_secs(), elapsed.subsec_nanos())
}

      이어서 저장소입니다(store.rs). DB 없이 BTreeMap에 담습니다(id 순서가 유지되므로 목록이 항상 id 오름차순입니다). id는 last_id를 1씩 올려 만들고 삭제해도 번호를 다시 쓰지 않습니다. axum이 요청마다 상태를 Clone하므로 TaskStore는 Clone이고, 안쪽의 Arc<Mutex<Inner>>가 모든 복제본이 같은 데이터를 가리키게 합니다. 락은 짧게만 잡고 .await를 넘겨 쥐지 않습니다(레슨 10의 MutexGuard 오류가 여기서 중요합니다). update는 보낸 필드(Some)만 덮어씁니다. 제목 검증과 "수정할 필드 없음" 거절은 저장소가 아니라 핸들러가 먼저 합니다(Spring이라면 서비스 계층이 하던 일입니다).

      use std::collections::BTreeMap;
use std::sync::{Arc, Mutex, MutexGuard};

use crate::clock::now_rfc3339;
use crate::model::{Task, UpdateTask};

#[derive(Clone, Default)]
pub struct TaskStore {
    inner: Arc<Mutex<Inner>>,
}

#[derive(Default)]
struct Inner {
    last_id: u64,
    tasks: BTreeMap<u64, Task>,
}

impl TaskStore {
    pub fn list(&self) -> Vec<Task> {
        self.lock().tasks.values().cloned().collect()
    }

    pub fn create(&self, title: String) -> Task {
        let mut inner = self.lock();
        inner.last_id += 1;
        let task = Task {
            id: inner.last_id,
            title,
            done: false,
            created_at: now_rfc3339(),
        };
        inner.tasks.insert(task.id, task.clone());
        task
    }

    pub fn get(&self, id: u64) -> Option<Task> {
        self.lock().tasks.get(&id).cloned()
    }

    pub fn update(&self, id: u64, changes: UpdateTask) -> Option<Task> {
        let mut inner = self.lock();
        let task = inner.tasks.get_mut(&id)?;
        if let Some(title) = changes.title {
            task.title = title;
        }
        if let Some(done) = changes.done {
            task.done = done;
        }
        Some(task.clone())
    }

    pub fn delete(&self, id: u64) -> bool {
        self.lock().tasks.remove(&id).is_some()
    }

    fn lock(&self) -> MutexGuard<'_, Inner> {
        self.inner
            .lock()
            .expect("Task 저장소의 락이 오염되었습니다")
    }
}
    3. 에러 타입과 IntoResponse, 전체 검색 (error.rs, 2단계 의존)

      핸들러가 돌려줄 에러를 enum으로 모으고, 각 에러가 어떤 상태 코드와 JSON 본문이 될지 IntoResponse에서 한곳에 정합니다. JsonRejection은 axum의 Json 추출기가 실패했을 때 쓰는 타입으로, 기본 응답은 잘못된 JSON 400, 모양이 안 맞는 JSON(모르는 필드, 타입 불일치) 422, 헤더 누락 415입니다. 이 레슨의 규약은 "본문을 읽을 수 없으면 400"이라서, 여기서는 MissingJsonContentType만 415로 두고 나머지는 400으로 바꿨습니다. 메시지는 접두어 요청 본문을 읽을 수 없습니다: 뒤에 axum이 만든 설명(body_text(), 영어입니다)을 붙입니다. NotFound의 문구는 할 일을 찾을 수 없습니다(id를 넣지 않음)입니다.

      use axum::Json;
use axum::extract::rejection::JsonRejection;
use axum::http::StatusCode;
use axum::response::{IntoResponse, Response};
use serde_json::json;

#[derive(Debug)]
pub enum ApiError {
    NotFound,
    Validation(String),
    InvalidBody(JsonRejection),
}

impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        let (status, message) = match self {
            ApiError::NotFound => (
                StatusCode::NOT_FOUND,
                "할 일을 찾을 수 없습니다".to_string(),
            ),
            ApiError::Validation(message) => (StatusCode::BAD_REQUEST, message),
            ApiError::InvalidBody(rejection) => {
                let status = match rejection {
                    JsonRejection::JsonDataError(_) => StatusCode::BAD_REQUEST,
                    _ => rejection.status(),
                };
                (
                    status,
                    format!("요청 본문을 읽을 수 없습니다: {}", rejection.body_text()),
                )
            }
        };
        (status, Json(json!({ "error": message }))).into_response()
    }
}

impl From<JsonRejection> for ApiError {
    fn from(rejection: JsonRejection) -> Self {
        ApiError::InvalidBody(rejection)
    }
}

    4. 핸들러와 추출기 (handlers.rs, 2~3단계 의존)

      이 레슨의 핵심 파일입니다. 먼저 위쪽에는 제목 길이 상수, 상태 확인 핸들러, 목록과 생성 핸들러가 있습니다. create_task는 State와 본문(Json)을 받고, 본문은 Result<Json<CreateTask>, JsonRejection> 형태로 받아 ?로 ApiError로 바꿉니다. 처리 순서는 이렇습니다. 본문 읽기, 제목 앞뒤 공백 제거, 빈 제목이면 400, 100자(chars().count()로 센 글자 수) 초과면 400, 저장, 201 응답입니다. 응답에는 Location: /tasks/{id} 헤더도 붙습니다.

      use axum::Json;
use axum::extract::rejection::JsonRejection;
use axum::extract::{Path, State};
use axum::http::{StatusCode, header};
use serde_json::{Value, json};

use crate::error::ApiError;
use crate::model::{CreateTask, Task, UpdateTask};
use crate::store::TaskStore;

const MAX_TITLE_CHARS: usize = 100;

pub async fn health() -> Json<Value> {
    Json(json!({ "status": "ok" }))
}

pub async fn list_tasks(State(store): State<TaskStore>) -> Json<Vec<Task>> {
    Json(store.list())
}

pub async fn create_task(
    State(store): State<TaskStore>,
    payload: Result<Json<CreateTask>, JsonRejection>,
) -> Result<(StatusCode, [(header::HeaderName, String); 1], Json<Task>), ApiError> {
    let Json(input) = payload?;
    let title = validate_title(&input.title.unwrap_or_default())?;
    let task = store.create(title);
    let location = [(header::LOCATION, format!("/tasks/{}", task.id))];
    Ok((StatusCode::CREATED, location, Json(task)))
}

      pub async fn get_task(
    State(store): State<TaskStore>,
    Path(id): Path<String>,
) -> Result<Json<Task>, ApiError> {

pub async fn update_task(
    State(store): State<TaskStore>,
    Path(id): Path<String>,
    payload: Result<Json<UpdateTask>, JsonRejection>,
) -> Result<Json<Task>, ApiError> {
    let id = parse_id(&id)?;
    let Json(mut changes) = payload?;
    if changes.title.is_none() && changes.done.is_none() {
        return Err(ApiError::Validation(
            "수정할 필드(title, done)가 없습니다".to_string(),
        ));
    }
    if let Some(title) = &changes.title {
        changes.title = Some(validate_title(title)?);
    }
    store
        .update(id, changes)
        .map(Json)
        .ok_or(ApiError::NotFound)
}

pub async fn delete_task(
    State(store): State<TaskStore>,
    Path(id): Path<String>,
) -> Result<StatusCode, ApiError> {
    let id = parse_id(&id)?;
    if store.delete(id) {
        Ok(StatusCode::NO_CONTENT)
    } else {
        Err(ApiError::NotFound)
    }
}

      나머지 두 함수는 id 해석과 제목 검증으로, 평범한 함수입니다.

      fn parse_id(text: &str) -> Result<u64, ApiError> {
    text.parse::<i64>()
        .ok()
        .filter(|id| *id >= 1)
        .map(|id| id as u64)
        .ok_or_else(|| ApiError::Validation("id는 1 이상의 정수여야 합니다".to_string()))
}

fn validate_title(title: &str) -> Result<String, ApiError> {
    let title = title.trim();
    if title.is_empty() {
        return Err(ApiError::Validation(
            "title은 비어 있을 수 없습니다".to_string(),
        ));
    }
    if title.chars().count() > MAX_TITLE_CHARS {
        return Err(ApiError::Validation(format!(
            "title은 {MAX_TITLE_CHARS}자 이하여야 합니다"
        )));
    }
    Ok(title.to_string())
}

      눈여겨볼 곳은 이렇습니다.

      • store.get(id).map(Json).ok_or(ApiError::NotFound): Option<Task>를 Result로 바꾸는 관용구입니다. Some이면 Json으로 감싸고, None이면 404 에러입니다.
      • PATCH 핸들러의 순서는 id 해석, 본문 읽기, 필드가 하나도 없으면 400, 제목이 있으면 검증, 저장소(없는 id면 404)입니다. 그래서 없는 id에 {}를 보내도 404가 아니라 400입니다.
      • Path<u64>로 받으면 /tasks/abc에서 axum의 기본 거절 응답(JSON이 아닌 텍스트 400)이 나갑니다. 문자열로 받아 직접 바꾸면 JSON 400 "id는 1 이상의 정수여야 합니다"를 돌려줄 수 있고, 0이나 -1도 같은 방식으로 거를 수 있습니다. 이 레슨의 Path<String>과 Json은 모두 ApiError로 감쌌습니다. 반대로 Path<u64>나 Query<T>처럼 변환이 실패할 수 있는 추출기를 그대로 쓰면 axum의 기본 거절 응답이 나갑니다. 레슨 12의 Query가 그 경우이고, 거기서 한 번 더 설명합니다.
      • 제목 검증은 어노테이션이 아니라 평범한 함수입니다. 검증 라이브러리(validator 등)도 있지만 이 레슨에서는 쓰지 않습니다.

      서버 없이 같은 app()을 테스트하는 파일입니다. send 도우미가 요청을 만들어 oneshot으로 보내고, 응답 본문을 JSON으로 읽어 (상태 코드, JSON)으로 돌려줍니다. app.clone().oneshot(...)에서 clone하는 것은 oneshot이 서비스를 소비하기 때문이고, 저장소는 Arc 안에 있어 복제본끼리 데이터를 공유합니다.

      use axum::Router;
use axum::body::Body;
use axum::http::{Method, Request, StatusCode, header};
use http_body_util::BodyExt;
use serde_json::{Value, json};
use tower::ServiceExt;

async fn send(app: &Router, method: Method, uri: &str, body: Option<&str>) -> (StatusCode, Value) {
    let mut builder = Request::builder().method(method).uri(uri);
    let body = match body {
        Some(text) => {
            builder = builder.header(header::CONTENT_TYPE, "application/json");
            Body::from(text.to_string())
        }
        None => Body::empty(),
    };
    let response = app
        .clone()
        .oneshot(builder.body(body).unwrap())
        .await
        .unwrap();
    let status = response.status();
    let bytes = response.into_body().collect().await.unwrap().to_bytes();
    let value = serde_json::from_slice(&bytes)
        .unwrap_or_else(|_| Value::String(String::from_utf8_lossy(&bytes).into_owned()));
    (status, value)
}

    Go 코스를 먼저 하셨다면: Task API 비교

    이 하위 절은 이 코스의 Go 편(레슨 09, 레슨 10)을 먼저 하신 분을 위한 참고입니다. Go 편을 하지 않으셨다면 건너뛰어도 됩니다. 두 코스가 같은 Task API를 비교할 수 있도록, Go 편의 서버(go/lab/lesson10)와 이 레슨의 서버를 함께 띄우고 같은 요청 70건 넘게 보내 상태 코드, 응답 본문, Location·Allow·Content-Type 헤더를 비교했습니다. 같았던 것은 다음과 같습니다.

    • 상태 코드: 생성 201, 삭제 204, 없는 id 404, 잘못된 입력 400. 에러 본문은 {"error":"..."}이고 문구도 같습니다.
    • PATCH는 보낸 필드만 고칩니다. {}는 400 "수정할 필드(title, done)가 없습니다"이고, 없는 id에 보내도 404가 아니라 400입니다.
    • 제목은 앞뒤 공백(NBSP·전각 공백·탭 포함)을 뗀 뒤 비어 있으면 400, 100자(이모지 100개는 통과, 101개는 거절)를 넘으면 400입니다. 제목이 없거나 null이어도 같은 400입니다.
    • 알 수 없는 필드(titel)는 400입니다. id가 abc, 0, -1, 64비트 정수 범위 밖이면 400 "id는 1 이상의 정수여야 합니다"입니다.
    • id는 1부터 커지고 삭제해도 재사용하지 않으며, 목록은 id 오름차순이고 비어 있으면 []입니다. JSON 필드 이름과 순서, created_at(소수점 아래 끝의 0을 뗀 RFC 3339 UTC), 생성 응답의 Location 헤더, 405의 상태 코드와 Allow에 든 메서드 목록도 같습니다.

    다른 점은 이렇습니다. 맞추지 않은 이유를 함께 적었습니다.

    • Go 레슨 09/10과 이 점이 다르다: Content-Type 검사입니다. Go 편의 서버는 헤더가 없거나 text/plain이어도 본문을 JSON으로 읽어 201(PATCH는 200)로 답하지만, axum의 Json은 application/json(또는 +json으로 끝나는 형식)이 아니면 415입니다. 이유: Json 추출기의 표준 동작을 보여 주는 것이 이 레슨의 목적이고, Go처럼 받으려면 본문을 Bytes로 받아 직접 파싱해야 해서 구현이 과해집니다.
    • Go 레슨 09/10과 이 점이 다르다: JSON 읽기가 더 엄격합니다. Go의 JSON 해석기(encoding/json)는 필드 이름의 대소문자를 구분하지 않아 {"Title": "x"}를 받고, 값 뒤에 다른 글자가 붙어도({"title":"a"} garbage) 같은 키가 두 번 나와도 받습니다. serde_json은 이 경우를 모두 400으로 거절합니다. 이유: serde의 기본 동작이고 더 엄격한 쪽이라, Go에 맞추려고 일부러 느슨하게 만들지 않았습니다.
    • Go 레슨 09/10과 이 점이 다르다: 본문을 읽지 못했을 때 오류 문구의 뒷부분입니다. 상태(400)와 접두어 요청 본문을 읽을 수 없습니다: 는 같지만, 뒤의 설명은 Go가 unexpected EOF, json: unknown field "titel"이라면 이 레슨은 serde가 만든 영어 문장(unknown field `titel`, expected `title` ...)입니다. 이유: 각 언어의 JSON 라이브러리가 만든 문장을 그대로 이어 붙이기 때문입니다.
    • Go 레슨 09/10과 이 점이 다르다: 본문 크기 제한입니다. Go 편의 서버는 제한이 없어(제한은 Go 편 레슨 10의 MaxBody 연습 문제에서 직접 만듭니다) 3MB 본문도 끝까지 읽어 제목 길이 400을 돌려주지만, axum의 Json은 기본 한도(2MB)를 넘으면 413입니다. 이유: axum의 기본 한도를 그대로 두었습니다.
    • Go 레슨 09/10과 이 점이 다르다: 알 수 없는 경로(/nope, 끝에 슬래시가 붙은 /tasks/)의 404 본문입니다. Go는 텍스트 404 page not found(text/plain), axum은 본문이 없습니다. 이유: Go도 JSON이 아니어서 맞출 이득이 작고, 맞추려면 fallback 핸들러를 더해야 합니다.
    • Go 레슨 09/10과 이 점이 다르다: 405 응답의 본문과 Allow 표기입니다. 상태 코드와 메서드 목록은 같지만, Go는 본문 Method Not Allowed(text/plain)에 DELETE, GET, HEAD, PATCH처럼 정렬해 쓰고, axum은 본문 없이 GET,HEAD,PATCH,DELETE로 씁니다. 이유: 위와 같습니다.
    • Go 레슨 09/10과 이 점이 다르다: 제목에 <, >, &가 있으면 Go의 JSON 인코더는 \u003c처럼 이스케이프해서 내보내고, serde_json은 그대로 내보냅니다. JSON으로 읽으면 같은 값입니다. 이유: 두 라이브러리의 기본 동작 차이입니다.
    • Go 레슨 09/10과 이 점이 다르다: 계층 구조입니다. Go 편은 요청 처리를 handler, service, repository 세 계층으로 나누고 인터페이스로 잇습니다(Spring의 Controller, Service, Repository와 같은 모양). 이 레슨은 핸들러가 검증까지 하고 저장소 TaskStore 하나만 씁니다. 이유: 분량 때문이고, 저장소를 trait으로 나누는 일은 레슨 12의 확장 과제입니다.
    • Go 레슨 09/10과 이 점이 다르다: 운영 기능입니다. Go 편 레슨 10의 서버에는 요청 ID(X-Request-Id 헤더), 구조화 로그, panic 복구, 우아한 종료(graceful shutdown)가 있고, 이 레슨의 서버에는 없습니다. 이유: 구현이 과해지고, 로그와 종료 처리는 레슨 12의 확장 과제로 다룹니다.
    • Go 레슨 09/10과 이 점이 다르다: 포트와 주소입니다. Go 편의 서버는 기본 8080(localhost)이고, 이 레슨은 3000(127.0.0.1)입니다. PORT 환경변수로 바꾸는 점은 같지만, 잘못된 값(abc)을 주면 Go는 오류를 내고 종료하는 반면 이 레슨은 3000으로 시작합니다. 이유: .vscode의 작업과 디버그 구성이 3000을 쓰도록 맞춰져 있습니다.

    정답 예시 보기 
    #[tokio::test]
async fn patch_updates_only_the_sent_fields() {
    let app = lesson11::app();
    send(&app, Method::POST, "/tasks", Some(r#"{"title": "운동"}"#)).await;

    let (status, task) = send(&app, Method::PATCH, "/tasks/1", Some(r#"{"done": true}"#)).await;
    assert_eq!(status, StatusCode::OK);
    assert_eq!(task["title"], "운동");
    assert_eq!(task["done"], true);

    let (_, task) = send(
        &app,
        Method::PATCH,
        "/tasks/1",
        Some(r#"{"title": "  아침 운동  "}"#),
    )
    .await;
    assert_eq!(task["title"], "아침 운동");
    assert_eq!(task["done"], true);

    let (_, task) = send(&app, Method::GET, "/tasks/1", None).await;
    assert_eq!(task["title"], "아침 운동");
    assert_eq!(task["done"], true);
}

    FIX자주 나는 오류

    따라하기에서 만난 E0277, E0308, 경로 문법 패닉, 포트 충돌 외에 서버에 요청할 때 자주 겪는 증상입니다. 응답은 모두 실제 서버에 보내 얻었습니다.

    증상: 서버가 시작하자마자 "포트를 열 수 없습니다"로 죽는다

    원인: 같은 포트를 다른 프로세스(이미 켜 둔 서버, 디버거)가 쓰고 있습니다. 해결: 켜져 있는 서버 터미널에서 Ctrl+C로 끝내거나, 다른 포트로 실행합니다(PowerShell $env:PORT = '4000', bash PORT=4000 cargo run -p lesson11). 메시지의 괄호 안 설명은 Windows 언어에 따라 다르게 나옵니다. 아래는 이미 서버가 켜져 있는 상태에서 한 번 더 실행했을 때의 출력입니다. cargo run으로 실행하면 이 뒤에 error: process didn't exit successfully: ... (exit code: 101) 한 줄이 더 붙고, 디버거로 실행하면 이 줄이 없습니다.

    cargo run -p lesson11
    thread 'main' (...) panicked at lesson11\src\main.rs:10:33:
3000번 포트를 열 수 없습니다: 각 소켓 주소(프로토콜/네트워크 주소/포트)는 하나만 사용할 수 있습니다. (os error 10048)
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

    증상: 415 Unsupported Media Type

    원인: Content-Type: application/json 헤더 없이 JSON 본문을 보냈습니다. curl은 -d만 쓰면 폼 형식 헤더를 붙입니다. 해결: -H "Content-Type: application/json"을 추가합니다(.http 파일에서는 헤더 줄을 빈 줄 앞에 둡니다). (Go 코스의 서버는 이 헤더 없이도 받아 주므로, 그 습관대로 보내면 여기서만 막힙니다.)

    curl.exe -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:3000/tasks -d '{"title": "x"}'
    {"error":"요청 본문을 읽을 수 없습니다: Expected request with `Content-Type: application/json`"}
HTTP 415

    증상: 400 — "요청 본문을 읽을 수 없습니다"

    원인: 본문이 올바른 JSON이 아닙니다. 가장 흔한 이유는 PowerShell의 인용 처리입니다. Windows PowerShell 5.1(powershell.exe)은 작은따옴표 문자열 안의 큰따옴표를 외부 프로그램에 넘길 때 벗겨 버려서 -d '{"title": "x"}'가 {title: x}로 전달됩니다(이 PC에서 5.1과 PowerShell 7을 나란히 실행해 확인했고, PowerShell 7.7에서는 정상 전달되었습니다). 서버가 받는 모양을 그대로 재현한 응답은 아래와 같습니다. 해결: PowerShell 7이나 bash를 쓰거나, 5.1에서는 큰따옴표를 \"로 이스케이프하거나, 본문을 파일에 담아 -d @body.json으로 보내거나, requests.http를 씁니다.

    curl.exe -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:3000/tasks -H "Content-Type: application/json" -d '{"title": "x"}'
    {"error":"요청 본문을 읽을 수 없습니다: Failed to parse the request body as JSON: key must be a string at line 1 column 2"}
HTTP 400

    위 명령은 Windows PowerShell 5.1에서 실행한 것이고, PowerShell 7이나 bash에서는 같은 명령이 201로 성공합니다. 괄호나 따옴표가 끝나지 않은 JSON도 같은 400입니다.

    curl.exe -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:3000/tasks -H "Content-Type: application/json" -d '{"title": '
    {"error":"요청 본문을 읽을 수 없습니다: Failed to parse the request body as JSON: title: EOF while parsing a value at line 1 column 10"}
HTTP 400

    증상: 400 — "unknown field" 또는 "title은 비어 있을 수 없습니다"

    원인: JSON 문법은 맞지만 필드 이름이 틀렸거나 title이 없습니다. titel처럼 오타가 난 이름은 deny_unknown_fields 때문에 "unknown field"로 거절됩니다. title을 아예 보내지 않으면({}) 제목이 빈 것으로 보고 검증이 실패합니다. 다른 axum 자료에서 필드 누락이 422로 나오는 것을 봤더라도, 이 레슨은 규약(본문을 읽을 수 없으면 400)을 지키려고 모두 400으로 바꿨습니다. 해결: 본문의 필드 이름을 title, done으로 정확히 씁니다.

    curl.exe -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:3000/tasks -H "Content-Type: application/json" -d '{"titel": "x"}'
    {"error":"요청 본문을 읽을 수 없습니다: Failed to deserialize the JSON body into the target type: titel: unknown field `titel`, expected `title` at line 1 column 8"}
HTTP 400
    curl.exe -s -w "\nHTTP %{http_code}\n" -X POST http://127.0.0.1:3000/tasks -H "Content-Type: application/json" -d '{}'
    {"error":"title은 비어 있을 수 없습니다"}
HTTP 400

    증상: /tasks/abc나 /tasks/0이 404가 아니라 400이다

    원인: id는 1 이상의 정수여야 합니다. 숫자가 아니거나 0 이하이면 저장소를 찾아보기 전에 400으로 거절합니다. 해결: 1 이상의 정수 id를 씁니다. 존재하지 않는 id는 404입니다.

    curl.exe -s -w "\nHTTP %{http_code}\n" http://127.0.0.1:3000/tasks/abc
    {"error":"id는 1 이상의 정수여야 합니다"}
HTTP 400

    증상: curl이 이상한 표 형식으로 출력하거나 -X를 인식하지 못한다

    원인: Windows PowerShell 5.1에서는 curl이 Invoke-WebRequest의 별칭입니다(이 PC의 powershell.exe에서 Get-Alias curl로 확인). PowerShell 7.7에서는 별칭 없이 curl.exe가 실행됩니다. 해결: 터미널 종류와 상관없이 curl.exe를 쓰거나 requests.http를 씁니다.
